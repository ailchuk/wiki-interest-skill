# wiki-interest: навичка для AI-агента

Навичка у форматі [Agent Skills](https://agentskills.io/specification). Вона відповідає на питання «чи зростає інтерес до теми і в яких мовах» за даними [переглядів Wikipedia](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/reference/page-views.html). Результат: таблиця метрик із рівнем довіри, два графіки та PDF на одну сторінку.

Уся навичка лежить у папці [wiki-interest/](wiki-interest/).

## Швидкий старт

Потрібно: `bash`, Python 3.10+, інтернет. Команди нижче запускаються з кореня репозиторію. На Windows `bash` дає Git Bash із [Git for Windows](https://git-scm.com/download/win) (його ж використовує Claude Code), а Python ставиться з python.org. Без Git Bash навичка запускається через `python wiki-interest/scripts/wi.py ...` і сама готує те саме середовище.

**Як навичка для Claude Code** (2.x):

```bash
mkdir -p ~/.claude/skills
cp -r wiki-interest ~/.claude/skills/
```

Далі просто запитайте агента, наприклад: «Чи зростає інтерес до астрономії в україномовній Вікіпедії?». Інші агенти, що підтримують Agent Skills, підключають папку `wiki-interest/` так само.

**Вручну, без агента:**

```bash
bash wiki-interest/scripts/wi find "астрономія" --langs uk --query-lang uk
bash wiki-interest/scripts/wi analyze Q333 --langs uk
```

Перший запуск сам створює `wiki-interest/.venv` і ставить залежності (`matplotlib`, `fpdf2`, `uharfbuzz`, 1–2 хв). Результати пишуться в `./wiki-research/`.

**Тести:**

```bash
cd wiki-interest
bash scripts/wi --help
.venv/bin/python -m unittest discover -s tests
```

## Як це працює

Чотири команди. Кожна робить цілий крок і друкує стисле зведення, тож агенту на дешевій моделі не треба писати код чи розбирати сирі дані.

| Команда | Що робить |
|---|---|
| `find "тема" --langs pl,cs --query-lang uk` | Шукає тему будь-якою мовою у Wikidata, показує назву статті в кожній мові. Якщо статті немає, пише `MISSING` і пропонує схожі, але нічого не вигадує. Перевіряє коди мов і підказує правильний. З кількома QID показує таблицю по всьому кошику й позначає мови, де є лише його частина. |
| `analyze Q1666254 --langs pl,cs` | Бере останні ≥24 завершені місяці, рахує метрики, рівень довіри, рейтинг мов, будує 2 графіки. Друкує команду для повтору, щоб уточнення коштувало одного параметра. |
| `check <run> --answer answer.md` | Перевіряє чернетку відповіді перед тим, як агент її надішле. Те, що код може вирішити сам у будь-якій мові (число не з даних, перевернутий знак, емодзі прапорця замість мовного розділу), блокує відповідь. Решту — пропущені обмеження, незгадані рівні довіри, мови без даних — друкує як чек-лист. |
| `report <run> --findings findings.md --lang uk` | Верстає PDF на 1 сторінку: висновки агента + таблиця, графіки, припущення й обмеження з даних. Якщо число у висновках не збігається з даними — включно з напрямом зміни й обсягом переглядів — PDF не створюється. Надписи 14 мовами (en, uk, pl, cs, de, es, fr, pt, tr, vi, ja, zh, ar, hi), для решти англійська. |

Метрики для кожної мови (деталі й пороги: [methodology.md](wiki-interest/references/methodology.md)):

- **Зростання:** останні 12 місяців проти попередніх 12. Порівнюються ті самі календарні місяці, тож сезонність зникає.
- **Без сплесків:** дні з новинним ажіотажем (у 3 рази вище звичайного) замінюються звичайним рівнем.
- **З поправкою на трафік вікі:** зміна частки статті серед усіх переглядів цієї Вікіпедії. Це головний сигнал, бо загальний трафік Wikipedia падає.
- **Довіра HIGH/MEDIUM/LOW з причинами.** Її рахує код, а не модель: обсяг переглядів, стабільність по місяцях, чи тримається зростання без сплесків і після поправки. Пороги обсягу можна змінити під нішу (`--low-views`, `--high-views`), бо «достатня аудиторія» для різних продуктів різна. Змінене значення автоматично потрапляє в назву теки прогону, команду повтору й припущення PDF, тож звіт не може збрехати про те, як рахувалась довіра.
- **Рейтинг:** за зростанням з поправкою, LOW внизу. Користувач може змінити критерій (`--sort volume`).
- **Рік до року:** з `--months 36` і більше кожен рік порівнюється з попереднім, а код ставить мітку `improving / worsening / about the same`.
- **Кошик статей:** широкий намір рідко є однією статтею. `analyze Q1860,Q490396` міряє «англійська мова + IELTS» як одну тему: перегляди мови — це сума її статей, а вивід показує розбивку по кожній. Мова, у якої є лише частина кошика, позначається окремо, бо інакше вона програвала б лише через меншу кількість врахованих статей.

### Ключові рішення

- **Логіку рахує код, модель лише інтерпретує.** Рівень довіри, рейтинг, обмеження й звірку чисел рахують скрипти, а обов'язкові застереження друкує сам `analyze`. Пробний прогін показав, що Haiku краще виконує вивід команди, ніж правила в SKILL.md.
- **Висновки перевіряються перед тим, як потрапити до користувача.** Не лише в PDF: `check` проганяє ту саму звірку чисел по чернетці відповіді в чаті. Перевірки поділені на дві групи — те, що код вирішує сам незалежно від мови відповіді, зупиняє агента кодом виходу 3, а те, що можна лише вгадати за формулюванням (обмеження, рівні довіри), друкується як чек-лист і ніколи не блокує. Так перевірка не дає хибних спрацювань на нормальній відповіді японською чи арабською.
- **Жодних вигаданих статей.** Мапінг мов іде через Wikidata. Перший приклад із завдання впирається саме в це: у польській Вікіпедії статті про інтервальне голодування немає.
- **Помилки кажуть, що робити.** Агент ніколи не бачить traceback: будь-яка відмова — це один рядок `ERROR:` із наступною дією, а код виходу розрізняє тип полагодження (2 — виправ ввід, 3 — виправ відповідь або висновки, 4 — мережа). Часткові відмови не зупиняють аналіз: мова без статті стає `MISSING`, хибна назва — `NO VIEWS`, недоступний шрифт лишає попередження замість зриву PDF. `SKILL.md` окремо забороняє обходити помилку вигаданими даними.
- **Кеш у файлах.** Завершені місяці не змінюються, тому повторні й уточнені запити не звертаються до API.
- **Python + 3 залежності** (`matplotlib`, `fpdf2`, `uharfbuzz`). Версії закріплені й ставляться на Python 3.10–3.14. Скомпільованих файлів у репозиторії немає.
- **Будь-яке письмо в PDF без роздування репозиторію.** Шрифти Noto для ієрогліфів, арабського письма, івриту, деванагарі, бенгальської й тайської `report` завантажує лише тоді, коли вони потрібні. Джерело закріплене на конкретному коміті й перевіряється за SHA-256. Арабське письмо й деванагарі розкладаються через HarfBuzz, арабський звіт вирівнюється праворуч.

## Як я перевіряв (у т.ч. код, написаний з AI)

1. **Незалежна звірка чисел.** Наші місячні суми порівняно з окремим місячним ендпоінтом Wikimedia (ті самі дані, що в pageviews.wmcloud.org): 6 мов × 24 місяці, **0 розбіжностей**.
2. **Юніт-тести (58)** на штучних рядах із відомою відповіддю: зростання, сплеск, сезонність, мало даних, стаття з'явилася посеред періоду, падіння всієї вікі, рік до року на 36 місяцях, незалежність метрик від довжини вікна, кошик статей (сума частин дорівнює цілому, неповний кошик названо в припущеннях), рейтинг, звірка чисел (перевернутий знак, вигаданий обсяг, арабські й повноширинні цифри), перевірка відповіді в чаті (в т.ч. що правильна відповідь українською не дає хибних спрацювань), markdown від моделі, повнота перекладів 14 мов, вибір шрифту за письмом, PDF рівно на 1 сторінку українською, англійською, японською й арабською.
3. **Графіки й PDF переглянуто очима.** Так знайдено й виправлено накладання легенди та підписів. Палітру перевірено валідатором кольорів на доступність для дальтоніків.
4. **Формат навички** перевірено офіційним валідатором: `pip install skills-ref`, потім `agentskills validate wiki-interest` → `Valid skill`.
5. **Прогони на Haiku 4.5** через Claude Code: запити із завдання дослівно, уточнення, власний критерій користувача і запити польською, японською та арабською ([prompts.md](wiki-interest/evals/prompts.md), [RESULTS.md](wiki-interest/evals/RESULTS.md)). 45 прогонів у 8 раундів, разом $3.04. У фінальному раунді одне питання займає 42–92 с і 5–9 викликів. Після кожного раунду я читав транскрипти, виправляв навичку і проганяв знову:
   - **Підміна теми.** Коли статті не було, модель підставляла ширшу («піст» замість «інтервального голодування»). Тепер заборона стоїть прямо у виводі `find`.
   - **Мова як країна, вигадані числа.** Модель називала мовні розділи країнами і вигадала суму переглядів. Тепер таблиця показує назву мовного розділу, а `analyze` друкує шаблон відповіді.
   - **Вада продукту в уточненні «візьми 3 роки».** Цифри не змінювалися, і модель робила хибний висновок. Тепер з'явилася динаміка рік до року з мітками, які ставить код.
   - **Відповідь у чаті ні на що не спиралася.** На найширшому прикладі 3 модель додавала причини, яких немає в даних, і пропускала обмеження; в уточненні ставила емодзі прапорця замість назви мовного розділу. PDF у тих самих прогонах був правильний, бо його захищає код. Тому з'явилася команда `check`, яка робить те саме для чернетки відповіді.
   - **`check` спершу зробив гірше.** Модель проганяла його чотири рази на відповіді, яка вже пройшла, і зрештою писала в чат свіже резюме, якого ніхто не перевіряв — 16 викликів і 151 с. Тепер команда прямо каже, що відповідь пройшла і що її треба надіслати дослівно: наступний прогін дав 5 викликів, 60 с, і в чат пішов саме перевірений текст.
   - **Відсутня стаття закривала тему.** Модель казала «виміряти неможливо» і зупинялась. Тепер `find` каже, у скількох розділах стаття є і в яких найбільших, що сама відсутність означає нішевість або непокриту тему, а не брак інтересу, і що велику мову можна проаналізувати окремо як глобальний сигнал — але ніколи не видавати за аудиторію тієї мови, якої бракує.
   - **Ця ж правка відкрила нову.** Модель почала викидати відсутню мову з аналізу й ставити на її місце англійську, називаючи це «глобальним інтересом». Тепер відсутня мова лишається в `--langs` і показується як `MISSING`, а інший розділ додається лише на прохання користувача. Заразом уточнив правило про мову: назвати розділ як гіпотезу для перевірки можна, стверджувати, чим саме користуються ті читачі, — ні.
   - **Широкий намір мірявся однією статтею.** Ані `SKILL.md`, ані підказка у `find` цього не змінили. Спрацювало інше: тепер навичка починається з вимоги назвати поняття, які охоплює питання — річ це одне поняття, дія щонайменше два. Після цього модель зробила два пошуки й проаналізувала `Q1860,Q1455178` як кошик.

Помилки, знайдені під час перевірки:
- **Claude Desktop на Windows без bash.** У локальному режимі агента немає ні `bash`, ні Python, тож навичка не запускалась узагалі, а модель перебрала 10 команд навмання. Тепер є вхід `python scripts/wi.py` без bash, а SKILL.md каже: якщо немає й Python, попроси користувача його встановити і зупинись.
- **Скопійована навичка не запускалась.** `cp -r` робочої папки переносив і `.venv`, а venv на новому місці не працює: pip падав, і Haiku відповідав «із загальних знань». Тепер `wi` перебудовує перенесене середовище, прибирає невдале встановлення, а при збої агент каже, що аналіз неможливий, і зупиняється.
- **Рейтинг за замовчуванням** спершу ставив мову з упевненим падінням вище за мову, де інтерес тримається. Виправлено й покрито тестом.
- **Падіння трафіку.** Для статті «Астрономія» в uk трафік людей упав на 60%, а трафік, позначений як боти, подвоївся. Причина: Wikimedia у 2025 перекласифікувала ботів ([джерело](https://diff.wikimedia.org/2025/10/17/new-user-trends-on-wikipedia/)). Тепер це обмеження автоматично потрапляє в кожен звіт.
- **Звірка чисел не бачила знаку.** Висновок «інтерес зростає: +34%» проходив на даних, де падіння 34%, бо порівнювались модулі. Тепер число з явним `+` або `-` має збігтися й напрямом, а без знаку, як у «впав на 34%», напрям несе текст, тому звіряється лише величина.
- **Абсолютні числа не перевірялися зовсім.** «4200 переглядів на день» проходило при реальних 6. Тепер звіряються й прості числа від 10 і вище.
- **Періоди до середини 2015 вигадували історію.** Pageviews API починається з 2015-07, тож запит на 150 місяців давав хибну причину «стаття з'явилась» і зростання `+3654%` проти майже порожнього базового року. Тепер період обрізається по даті старту даних, і `analyze` про це повідомляє.
- **Головна метрика повзла від `--months`.** Той самий запит давав −48% на 24 місяцях і −47% на 36, бо локальна медіана для сплесків мала урізане вікно на перших днях базового року. Тепер перед періодом довантажуються 14 днів розігріву, і всі вікна дають однаковий результат.
- **Помилки вводу падали в traceback.** `--end 2026` віддавав сирий `ValueError`. Для дешевої моделі це найгірший вивід: він не каже, що робити. Тепер формат перевіряється, а `main()` ловить `ValueError` і `OSError`.
- **Нова перевірка сама давала хибні спрацювання.** `check` вважав рівень довіри пропущеним, коли модель писала «НИЗЬКІЙ» замість словникового «НИЗЬКА», і блокував число 20, хоча `analyze` друкує його в кожному поясненні LOW. Тепер слова довіри звіряються за основою, а пороги вважаються надрукованими значеннями.

## Приклади

PDF, який Haiku 4.5 сам згенерував на приклад 3 із завдання ([PDF](wiki-interest/evals/examples/ex3-english-learning-report.pdf), [findings.md](wiki-interest/evals/examples/ex3-findings.md)). Тема тут виміряна як кошик із двох понять, і в таблиці видно «+1» у тих мов, де є обидві статті, а в припущеннях — що в в'єтнамській і польській кошик неповний:

![Звіт: інтерес до англійської в 6 мовних розділах](wiki-interest/evals/examples/ex3-english-learning-report.png)

Висновки й рекомендацію Haiku лишено без правок, разом із вадами моделі. Таблицю, графіки, припущення й обмеження верстає код, їх перегенеровано під поточну версію. Усі числа в ньому з даних, це перевірив `report`. Але є дві речі, яких код не ловить:
- **Гіпотези про ринок.** Рекомендація називає «насичення ринку, міграцію на інші платформи, геополітичні фактори» як те, що варто перевірити. Таких речей перегляди не показують.
- **Причина MEDIUM.** Звіт пояснює її «дисперсією в даних», а в `analyze` причина інша: після поправки на трафік вікі тренд змінює напрям.

Ще одна межа стосується кошика. Другу статтю, «second-language acquisition», обрав сам Haiku. Вона дає до 6 переглядів на день, а стаття про саму мову 220–850, тож на практиці тренд визначає одна стаття. SKILL.md як приклад пропонує IELTS, але код не може оцінити, чи вдало модель склала кошик.

Ці випадки описані в [RESULTS.md](wiki-interest/evals/RESULTS.md), розділ «Known limits».

Той самий формат арабською, справа наліво ([PDF](wiki-interest/evals/examples/ar-astronomy-report.pdf)): звіт Haiku на запит арабською.

## Обмеження

- Перегляди показують цікавість, а не готовність платити.
- Мовний розділ не дорівнює країні.
- Набір статей для кошика має задати користувач або агент: автоматичного добору споріднених понять (підкласи Wikidata, категорії) поки немає, тож повнота теми залежить від того, які QID вибрали.
- Перегляди через редиректи (старі назви) не додаються. Перейменування посеред періоду дає довіру LOW.
- Причини й ринкові твердження — єдине правило, яке код не вміє перевірити: `check` може лише нагадати. У прогонах модель тепер здебільшого переводить такі здогадки в «що перевірити далі», але фраза на кшталт «ринок насичений» усе ще може дійти до користувача.
- Надписи PDF є для 14 мов, для решти англійська. Переклади зроблено з AI і не перевірено носіями мов. Графіки мовою звіту лише для латиниці й кирилиці, для інших письмен англійською, бо matplotlib не розкладає арабське письмо й деванагарі. Для ієрогліфів і арабського письма потрібен інтернет при першому звіті (завантаження шрифту).

## Як розвивати далі

1. **Більше тестових запитів.** Регулярно проганяти їх на дешевій моделі після кожної зміни SKILL.md, стежити за кількістю викликів і вартістю.
2. **Автоматичний добір кошика.** Сам кошик уже є, але його склад задають вручну. Наступний крок — пропонувати споріднені поняття через Wikidata (підкласи, `part of`) і категорії, щоб агент не мусив угадувати, з чого складається «вивчення англійської».
3. **Великі обсяги.** Замість API для кожної статті брати [bulk-дампи переглядів](https://dumps.wikimedia.org/other/pageview_complete/) у Parquet + DuckDB. Тоді можна за хвилини проглядати всі ~350 Вікіпедій і тисячі статей.
4. **Ринок, а не мова.** Дані переглядів за країнами, кількість мовців, інтернет-аудиторія, купівельна спроможність.
5. **Інші сигнали.** Google Trends, запити в app stores, соцмережі, бо інтерес у Вікіпедії не дорівнює готовності платити.
6. **Аналітика.** Декомпозиція сезонності на рядах від 3 років, детекція точок зміни тренду, підписи новинних подій на графіку.
7. **Графіки будь-якою мовою.** Розкладка арабського письма й деванагарі в matplotlib або малювання графіків разом із текстом у PDF. Переклади надписів перевірити з носіями мов.
8. **Жорсткіша перевірка відповіді.** Зараз `check` блокує лише те, що перевіряється незалежно від мови. Наявність обмежень шукається за основами слів із 14 локалей, тож синонім може прослизнути. Надійніше — hook, що запускає `check` автоматично перед кожною відповіддю, і окрема модель-суддя для змістових тверджень.

## Структура

```
wiki-interest/
├── SKILL.md                  інструкції для агента
├── requirements.txt          закріплені залежності
├── scripts/
│   ├── wi                    точка входу, сама створює .venv
│   ├── bootstrap.py          те саме без bash: python scripts/wi.py
│   ├── wi.py                 команди find / analyze / check / report
│   ├── wikiapi.py            Wikimedia API + кеш
│   ├── metrics.py            метрики, довіра, рейтинг
│   ├── render.py             графіки, PDF, звірка чисел
│   ├── answer.py             перевірка чернетки відповіді в чаті
│   ├── fonts.py              шрифти Noto для інших письмен (завантаження за потреби)
│   ├── i18n.py               завантаження надписів
│   └── locales/              надписи PDF 14 мовами
├── references/methodology.md метрики, пороги, обмеження
├── tests/                    юніт-тести
└── evals/                    тестові запити, скрипт прогону, результати, приклади
```
